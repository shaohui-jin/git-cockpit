## 1. 项目概述

**项目名称**：Git Cockpit（展示名；npm 包：`@shaohui_jin/git-cockpit-mcp-server`，CLI：`git-cockpit`，完整命名规范见 11.1 节）  
**项目定位**：基于 MCP 的 Git 可视化操作工具：Web 界面 + 供外部 Agent 调用的 MCP 工具，支持多仓库与安全的 Git 操作。选边不由模型做。可选在同一 Web 内聊天（`/api/chat`，SDK 只在 server；模型 Key 在设置页，与 MR Token 同级）；桌面 Electron 是可选宿主，不是第二套后端。方案见 [聊天壳方案.md](./聊天壳方案.md)。  
**当前形态**：一个 npm 包三种入口——**MCP Server**、**Web**、**CLI**（`git-cockpit start` / `mcp`），另可选桌面窗壳。**不做** Cursor/VS Code 扩展。配 MCP **不等于**打开聊天页。

**核心价值**：

- **工具给宿主用**：Cursor、Claude 等通过 MCP 调用 `git_status` 等；也可在本机 Web/桌面聊天页调同一套手（确认闸在 `/api/chat`）。
- **可视化交互**：浏览器内完成暂存、提交、分支、stash、拉取/推送等。
- **安全可控**：高风险默认禁用；写操作 dry-run 预览 → 确认 → 执行；高危自动备份；审计日志。
- **唯一后端**：Web 与 MCP 共用 Runtime / GitService，队列与锁全局生效。

## 2. 目标用户与使用场景

### 2.1 目标用户

- 前端/全栈开发者，希望在聊天窗口里用 Agent 辅助 Git（通过 MCP 工具）。
- 不熟悉 Git 命令行的开发者，需要可视化界面。
- 团队协作者，需要审查历史、查看差异。
- 希望用 MCP 把 Git 接进 Agent 工作流的用户（在 **编辑器聊天窗口** 里操作，不是打开 Cockpit 内置对话）。

### 2.2 典型场景

1. **宿主辅助提交**：用户在聊天窗口说「看看当前改动并提交」，宿主模型调用 `git_status`、`git_diff`，再调用 `git_add` 和 `git_commit`。
2. **历史分析**：宿主调用 `git_log` / `git_show`，在对话里回答关于代码变更的问题。
3. **可视化手动操作**：用户在 Web 状态页勾选文件、暂存、提交、推送；操作前弹出 dry-run 预览确认框。看提交记录在状态页切到「提交」，不必另开一页。
4. **选择性 stash**：勾选部分文件 stash（对应 IDE Shelve），可 apply / pop / drop，并查看 stash diff。
5. **多仓库切换**：打开多个本地仓库。工作台卡片按拖拽 `pin_order` 排列（新仓在队尾）；`last_opened_at` 只显示在卡片上，并作为 MCP 未指定仓时的默认仓。状态/合并视图跟随当前仓库刷新。
6. **权限治理**：在设置页开关高风险工具、配置审批名单；被拒操作会引导前往设置。
7. **合并预演、矩阵、选边与落盘**：网页选 `into`（合入目标 / ours）与 `from`（我的分支 / theirs），`merge-tree` 预演不改工作区；多分支用矩阵扫描、可建议合入顺序。从矩阵进单对：三栏选边后「完成冲突处理」只写入本地 `merge/…`（`push: false`），再回矩阵看「已解决·本地」，再在矩阵上推送该临时分支、申请 MR。从底栏进合并单对：干净可落盘并推送；有冲突必须人在网页选边。宿主聊天窗口只预演；有冲突给 `webUrl`，**不要**传 `files` 选边。开 PR/MR 先过 `mergeGate`（冲突/未落盘不能开，含 dry_run）。不把多条 from 合成一条批量分支。

`git_rebase_abort` / `git_rebase_continue` 是 **write**（结束已经开始的 rebase），不在默认禁用名单。开始变基才是 `git_rebase`（dangerous）。拣选 `git_cherry_pick` / `git_cherry_pick_continue` / `git_cherry_pick_abort` 也是 write：一次一个提交，冲突回状态页三栏；已经在当前分支上、或工作区正在 merge / rebase / cherry-pick 时拒绝。空拣选只中止，不跳过。

### 4.2 Web 可视化界面（已实现）

外壳为 **顶栏 + 底栏 dock**。干活为工作台 / 状态 / 合并；系统为任务（进行中角标）/ 操作日志 / 设置。已配置模型 Key 时聊天在底栏更靠前，并从底栏升起 overlay：升起动画、底边避开 dock、`z-index` 低于确认框/对话框；换仓清空可见会话并作废该仓 `sessionId`；确认条贴在输入框上方，仍走 `confirmChat`。一期能力边界文案保留。没有「历史」入口；看提交走状态页。打开应用仍进工作台，不默认进聊天。**任务 / 日志 / 设置**信息结构不变，卡片走 `.gc-glass`。**合并**单对为两条河 + 芯片档；冲突仍用现网三栏选边；矩阵格走 `--gc-matrix-*`。**Git 操作**左栏默认行为、右栏按域芯片墙。状态页提交列表与操作日志同款自定义行表。

- **工作台**（`/` → `/dashboard`，`/repos` 重定向）：打开本地路径、克隆入口、多仓脉搏。默认**卡片墙**：摘要数字筛卡住（不可用 / merge|rebase / 冲突）/ 有更改 / 未同步（↑↓ 或本地 `merge/*`），一仓只进一类；卡上名称、分支、该亮的标记，底栏近 12 周按日热力（周一为一周起点，7×12，`git log --all --date=short`，不读 diff）。点选当前仓（当前卡抬起，其余压暗）；拖拽改顺序并写入 `pin_order`。卡片右上角 ⋯（菜单挂 body）：进入去状态，合并去 `/merge`，可抓取这一仓，移除不删磁盘。双击卡片进入工作区。卡上显示上次打开时间。打开成功后留在工作台。数据：`GET /api/repos/overview` 与 `git_repo_overview`（MCP 默认只留 `activityTotal`，`detail` 才回 `activity[]`）。页面英雄卡 + 天气条 + 仓库一览。不轮询，进页或 fetch 完成后（`repo-changed`）再拉。「刷新」对全部可用仓起 **一条** `POST /api/jobs` `kind=fetch`（`payload.repoIds`；同仓 survey/fetch 互斥；不改工作区；丢失仓跳过）。**克隆到本地**：填 URL（禁止夹带 token / userinfo）与绝对空目录，`POST /api/jobs/clone` 起后台任务；目标路径须过 `allowedRepos`。提交后右上角 Notification（点击进 `/jobs?id=`），不在工作台堆任务列表。
- **任务**（`/jobs`）：左右分栏，**无抽屉**。左栏宽约 360px：按 `startedAt` 倒序，进行中始终置顶；顶上芯片筛全部 / 进行中 / 失败 / 成功（带数量）。每行：状态、kind 标签（克隆 / 矩阵扫描 / 抓取）、相对时间、标题（克隆为 URL→路径，抓取/扫描为「操作 → 仓库路径」，旧任务 title 不含路径则用 `repoPath` 补上）、日志尾或错误。**不按 kind 分组**。点一行写入 `?id=` 并 `GET /api/jobs/:id` 拉详情；右栏常驻该任务日志（`logs.join('\n')`，处理 `\r`）。进页若带 `?id=` 则选中该条。当前筛里没有已选任务时，改选可见第一条；筛空则清空 query。无任何任务时提示去工作台克隆；当前筛无匹配时提示「没有这类任务」；未选中时右栏提示点左侧。进行中可 `POST /api/jobs/:id/cancel`（克隆杀进程并删除不完整目标目录）。失败且 kind=clone 可改 URL/路径重试。`git clone --progress` 用 spawn（不走当前仓 GitService 队列，simple-git.clone 会整段缓冲）。任务写入 SQLite `jobs`（进行中约 200ms 落盘，结束强制写；旧 `clone_jobs` 启动时迁入后删除）；进程重启时 `running` → `error`（「服务重启，任务中断」）。SSE `job-progress` 约 200ms 节流，漏掉的 `chunk` 会攒到下次推送；结束只推 `ok`/`error`，前端再拉详情，并再弹成功/失败 Notification（点击进该任务）。成功后 `repoManager.open` 加入列表。底栏「任务」显示进行中数量。
- **状态视图**（`/status`）：右上角切 **工作区 | 分支图 | 提交**（只换右侧，不换仓）。
  - **工作区**（写操作）：左侧分支树（本地 + 远程分组，↑↓ 同步信息，数据来自分支 store；**双击切换**；**右键菜单**切换 / 拉取推送 / 删除，单例、宽 `--gc-ctx-menu` 100px）。中栏：未暂存 / 已暂存 / 未跟踪 / 全部；**更改列表按路径树**（目录在前，叶子为文件名；保留 A/M/? 方块与暂存/差异操作；目录勾选覆盖子文件；行高 `--gc-line`、左右 `--gc-pad`）。勾选后暂存或选择性 stash。点文件写入右侧 **差异监视器**（DiffViewer，不再开抽屉）；Stash 的「差异」也进监视器。stash / 备份 / worktree / reflog 合在「记录」卡片里，叠在监视器下面。提交、建分支、**工作区合并**、Fetch、打标签、硬重置、清理未跟踪、变基、强制推送。worktree 只提供列表/添加/删除，不在 linked worktree 里做 merge。工作区处于 merge/rebase 时告警条提供「完成选边并继续 / 中止」，三栏写回当前工作区（index `:1/:2/:3`），**不是** `git_apply_resolve`。
  - **分支图**：**收起左树、右侧铺满**。tip DAG（`for-each-ref` + `rev-list --parents`，G6 dagre），节点是各分支 tip 不是每条 commit，与 Git Insight 同口径。图上方可选 into/from **对比**，有共同祖先时画布切成三节点 Y 图（分叉点 / 线上 / 我的）。不在此模式切分支。
  - **提交**（`CommitLogPanel`）：同样收起左树、铺满。范围：当前分支（HEAD）/ 全部分支 / 指定分支（面板内树选，可含远程）；路径过滤、条数 20/50/100。过滤条与表格与操作日志同款（`.gc-glass` + 自定义行表，行高 `--gc-line`）。点击行打开差异抽屉：标题行（`--gc-line`）为提交说明 + 短 hash；下一行 meta：作者 · 时间 · refs（过长省略）· 文件数与 +/-（REST 把 `stats.insertions/deletions` 摊到顶层）。有 body 时默认收起。不从已收起的左树点选来过滤（避免与工作区双击切换同一套手势）。独立路由 `/history` **已删除**，无 redirect。
- **合并视图**（`/merge`，底栏一项；`/matrix` 重定向到 `?mode=matrix`）：芯片切 **单对预演 | 矩阵**；单对两条河选 from/into。状态在 `useMergeSessionStore`（内存，换仓清空，不写 SQLite）。
  - **单对**：`BranchTreeSelect` 选合入目标 `into`（线上 / ours，远程组优先）与我的分支 `from`（theirs）；可选非交互 fetch；预演得到 `situation`。有冲突时 `ConflictResolvePanel` 三栏（**线上 | 结果 | 我的**）；当前文件按需 `git_merge_blame` 显示两侧最近改的人（不是自动选边）。绿/蓝块网页可 auto，红块必须人点。按钮随档位：干净→落盘；`temp_local`→推送；`temp_remote` / 已推的临时枝→申请 MR；`already_merged`→无需操作。从矩阵进来：「完成冲突处理」只 `push: false` 记本地 `merge/…`，然后回矩阵。下拉不列 `merge/*` 当线上目标。
  - **矩阵**：多选 into / from，`git_merge_survey` 画格子。「去预演」或「开始逐条处理」切到单对记录选边（不推送）；回矩阵后冲突格若已有本地临时分支显示「已解决·本地」（merge-tree 结论仍是冲突，因为 from/into tip 没变）。矩阵统一处理顺序：先清剩余冲突，再 `git_push` 指定临时分支（不切换当前工作区），然后「申请 MR」。干净格源=from；已推临时分支源=临时分支。本会话开过的 PR/MR 记在 Pinia。SSE `repo-changed` 标矩阵可能过期。恰好 1 个 into 且 ≥2 个 from 时可 `git_merge_order`。不改工作区。不把多条 from 合成一条批量分支。
- **DiffViewer**（状态页工作区监视器 / 提交抽屉共用）：`diff2html.parse` 拆文件；短文件默认展开，**变更行 ≥200** 或 `pnpm-lock.yaml` / `package-lock.json` / `yarn.lock` 默认收起，点整行文件头才 `html()`（结果缓存，再折再开不再算）。行号为表格单元格（非 absolute），左右各约 4.5em，与 `+/-` 同行着色。
- **操作日志**：Web / MCP / CLI 来源，按工具过滤，参数已脱敏。行高走全局 `--gc-line`，结果单行。
- **设置**（`/settings`，默认进 **MR 配置**；Git 操作用 `?tab=git`；正文规范用 `?tab=template`。高风险被拒引导 Git 操作 Tab；缺 Token 引导默认 MR Tab）：
  - **MR 配置**：默认远程为当前仓 `listRemotes()` 下拉（存 `mr.defaultRemote` 名），展示 URL 与识别出的平台；未识别时手动选 GitHub / GitLab。开单方式为可点卡片 **A 本机 CLI / B Token / C 浏览器页**（无 Insight 的下载 CLI，也无「自动」链式回退）；只展开当前方式。点选后按**当前仓库路径**写入 `mr.repoMethods`；该仓从未点过则默认 **C**。旧全局 `mr.method` 只作读盘兼容，不套到新仓。**Token / 平台按 remote 的 hostname**（`github.com/org/a.git` 与 `github.com/org/b.git` 共用一条 `hosts[]`）；开单方式仍按本机绝对路径，换仓不会自动带上 A/B。平台跟当前选中 remote：GitHub 只显示 gh / GitHub Token，GitLab 只显示 glab / GitLab Token。
  - **A**：一行状态 **未下载 / 未登录 / 已登录**。未下载时同行「去下载」（gh → `https://cli.github.com/`，glab → GitLab CLI releases）。探测合并 Windows 用户/系统 Path 与常见安装目录，不依赖当前进程 PATH，**不下载** CLI。已登录时用 `gh auth token` / `glab auth token` 走与 B 相同的 API 校验，摘要如 `有效 · login · 至 2027/08/19 00:00:00`（凭证不进 GET 响应）。
  - **B**：Token 绑定当前远程 hostname；创建 Token 链接与「自建 / API Base URL」同一行。输入框不回填明文，展示掩码（如 `ghp_••••abcd`）。保存前格式校验 + GitHub `GET /user` / GitLab `GET /user`（及 PAT self），失败 400 且不落盘。Node `fetch` 在校验与开 PR 前 `trustSystemCa()`，合并系统 CA（本机 HTTPS 代理把 `api.github.com` 指到 127.0.0.1 时，不再只报 `fetch failed`）。进 MR Tab 或「重新校验」时 `GET /api/settings?validateToken=1`。
  - **当前远程凭证**：只列出与当前 hostname 相同、且已识别为 GitHub/GitLab 的那一条，可整条删除。表单内无「清除已保存 Token」。其它实例的 Token 不在本页展示。
  - **正文规范**：导入 Markdown 转字段表，写入 `mr.template`。启用后网页弹层与 MCP `git_mr_create` 都必须按 `fields` 填，服务端渲染同一份 body。开单方式为浏览器页时，结果带回正文供复制，并提示改用 Token / CLI。
  - **Git 操作**：左栏 `dryRunDefault` / `allowedRepos`、本机访问密钥复制；右栏按域芯片墙启用或禁用。空名单不限制路径。没有审批队列。

- **实时同步**：`EventSource /api/events` 收 `repo-changed` 与 `log`，全局 revision +1，各视图自动刷新。
- **交互约定**：写操作一律先 `dryRun: true` 再弹确认框（展示将执行的 `git` 命令与风险），确认后才真实执行；高风险被拒时引导设置「Git 操作」Tab。

## 6. 核心实现逻辑

阅读代码时按这条链路走即可。

### 6.1 进程入口

1. `git-cockpit` → `cli-entry.ts` → `cli.main(argv)`。
2. `start` 创建 **一次** `createRuntime({ dataDir })`：`trustSystemCa()`、读配置、打开 SQLite、装配 Permission / RepoStore / RepoManager / eventBus。`JobManager` 不在 Runtime 里，由 `createWebServer` 用同一 `db` 构造。
3. `mcp`：**先探活** `http://{host}:{port}/api/health`（只构造 `ConfigStore` 取端口与密钥，**不打开 SQLite**）。
   - 探到 daemon：`startMcpBridge()` 把 stdio 的 JSON-RPC 转发到 daemon 的 `/mcp`，会话 id 由桥回写传递 → 多客户端共用 daemon 的同一份队列与锁；
   - 探不到 daemon：当前 `mcp` 命令创建一次 Runtime + Web/MCP daemon，再桥接到它；stdin 关闭时若 daemon 属于当前命令则一并关闭；
   - 已有 daemon 但桥接失败不再静默降级为独立 Runtime，避免队列、SQLite 和仓库池分裂；地址统一由 `resolveDaemonEndpoint` 解析，支持 IPv6。
4. `start`：`createWebServer(runtime)` 监听端口；同进程挂 REST、SSE、`/mcp`、静态前端。SIGINT/SIGTERM 时 `server.close()` → `disposeRuntime`。

### 6.2 Runtime 与仓库池

`Runtime` 是进程内单例：一份配置、一个 DB、一个权限管理器、一个 `RepoManager`。

`RepoManager` 行为：

- 打开仓库时 `GitService.open`：`rev-parse --show-toplevel` 得到真实根目录，拒绝非 git 目录。
- 每个仓库根路径对应 **一个** `GitService`（懒创建，并对同一路径的并发 open 去重），Web 的 `repoId` 与 MCP 的 `repoId/repoPath` 命中同一实例。
- 写成功后 GitService 发 `changed` → RepoManager 转到 `eventBus 'repo-changed'` → SSE 推前端。
- 已打开列表在 SQLite `opened_repos`（`pin_order` 工作台顺序；`last_opened_at` 最近打开）。`activate` 只刷新 `last_opened_at`。`PUT /api/repos/order` 保存拖拽顺序。

仓库解析优先级（`executeTool`）：`ctx.repoId` > `ctx.repoPath` > `args.repoPath` > 最近打开的一条。都没有则报 `NO_ACTIVE_REPO`。

### 6.3 executeTool 安全链路（最重要）

MCP 回调与 `POST /api/repos/:id/tools/:tool` **共用** `executeTool`，内部转调 core `executeCapability`。顺序固定：

```
1. 权限  PermissionManager.assertAllowed(tool)
2. 参数  def.schema.parse(rawArgs)（zod）
3. 仓库  host.resolveRepo → GitService（优先级 repoId > 上下文 repoPath > args.repoPath > 最近打开）
4. 备份  非 dry-run 且 risk===dangerous 且 backupOnDangerousOps
         → BackupManager.createBackup()（stash -u + backup/pre-op-{ts} 分支）
5. 执行  def.handler → GitService 方法（dryRun 时只返回 WritePreview）
6. 审计  AuditLogger.log（参数按 logging.redact 脱敏）
         失败分 result=error / denied；不向调用方抛异常，编码进 error 字段
```

`dryRun`：参数显式传入优先，否则用 `permissions.dryRunDefault`。

MCP 文本输出由 `formatResultForMcp` 拼接：失败前缀「需要审批」或「操作失败」；成功时附 dry-run 标记、备份信息、一行 `next: 工具名`，再 JSON。JSON 对象上附结构化 `next[]`（`{ tool, args }`），不把现有结果改成 `{ ok, summary, detail }` 信封。Web `POST /tools` 的 `result` **不附** `next`。

Web 前端 `useToolAction`：先 `runTool(..., { dryRun: true })` → `ConfirmDialog` 展示命令 → 再无 dryRun 执行。403 + `requiredApproval` 弹框引导 `/settings?tab=git`。缺 Token 引导 `/settings`（默认 MR 配置）。

### 6.4 GitService

- 所有命令 **数组传参、无 shell**，避免注入。日常读写走 `simple-git.raw`；`runAllowFail` 用 `spawn` 同时拿 stdout / stderr / exit code（merge-tree 冲突时 exit 1 仍是有效结果）。
- 内部 `enqueue` 串行；写前检查 `.git/index.lock`。
- `validateRepoRelativePath` 拒绝绝对路径与 `..` 越界；`validateRefName` 拒绝 `;|&`$`、空格及 git 非法 ref 字符。
- 错误转成 `GitOperationError`（带 code），并对「无提交 / 推送被拒 / 合并冲突」等给出中文提示。
- diff / 文件内容默认 2MB 截断。

**合并预演与落盘**（`gitService.ts` + `merge.ts`）：

- 方向写死：`into` = 合入目标（远程 / ours），`from` = 我的分支（theirs）。规范化后同名（如 `master` 与 `origin/master`）直接拒绝，请用户自行 push/pull。
- 预演只用 `git merge-tree --write-tree`（Git **≥ 2.38**，过低报 `GIT_TOO_OLD`，禁止退回工作区 `git merge`）。不改工作区、不切换 HEAD。
- `git_merge_rehearse` 在预演之上用临时目录跑 `merge-file --diff3`，返回冲突正文；仍不改仓库。网页用 `diff` 包把 ours/theirs/base 收成 hunk（`buildChangeHunks.ts`），三栏展示；落盘时把各文件 `resolvedContent` 交给 `git_apply_resolve`。
- `git_merge_blame` 对单个冲突文件两侧 tip 跑 `git blame --line-porcelain`（按 `diff -U0` 新侧行号），不改工作区；网页切文件时按需拉取。
- `git_apply_resolve` 在独立 worktree 里基于 `into` 建临时分支、merge `from`、写入已解决 `files`、可选 push；主工作区全程不切换。worktree 的创建/删除排进 **主仓库队列**。网页从矩阵进来时传 `push: false` + `keepLocal: true`（只留本地临时分支）；合并页单对默认有远程则 push。矩阵上再对指定临时分支调 `git_push`（不 checkout）。
- 落盘成功时可拼浏览器创建页（GitHub compare / GitLab `merge_requests/new`）→ `createMrUrl`。
- **矩阵与合入顺序**（`survey.ts` / `chain.ts`）：`surveyMerges` 整批只 fetch 一次，格子只给路径；同名记 `same`，坏引用记 `error` 不拖垮整批。`suggestMergeOrder` 用 `commit-tree` 造游离 commit 往下推（作者写死 `git-cockpit@localhost`，不依赖仓库 user.email）；目标是 cleanPrefix，第一处冲突即停。贪心顺序对比传入顺序。不新建分支、不改工作区。
- **开 PR/MR**：`prepareMr` 用 `listRemotes()` / `listBranches()` 解析源/目标；远程名从 `into` 前缀或 origin/第一个 remote 推。`createPullOrMergeRequest` 用 `methodForRepo(mr, cwd)`（`mr.repoMethods` 按规范化仓库绝对路径）；该仓无记录则 **browser**。`git_mr_prepare` 带回 `method`。browser 只返回创建页 URL + 渲染正文（请复制粘贴），不写到远程；规范启用时提示改用 Token / CLI。Token / `apiBaseUrl` 按 **当前 remote 的 hostname** 查 `mr.hosts[]`。找不到 CLI **不下载**，返回官方安装地址。Token **禁止**作为工具入参。ssh → https 只走 `toHttpsRemoteUrl`。
- **fetch**：`fetch --prune --no-tags`；只更新远程跟踪引用，不改工作区、不合并。预演页可选先 fetch；状态页有 Fetch 按钮。`fetchQuiet` 仍给预演内部用，与工具 `git_fetch` 分开。
- **临时枝**：新名字 `merge/<slug-from>-into-<slug-into>--<from8>-<into8>`（`--` 才能和旧的 `merge/<from>-into-<into>` 并存）。旧名仍认，但提交里必须同时含两侧 tip，否则矩阵不当作进度。落盘或推送失败时，临时枝回到落盘前的 tip；这次新建的枝则删掉。
- **工作区 merge/rebase/cherry-pick 收尾**（已开始的冲突，不是预演）：`getStatus().operation` 为 `merge` / `rebase` / `cherry-pick`。`listWorkspaceConflicts()` 读 `ls-files -u` 的 `:1/:2/:3`。`mergeContinue` / `rebaseContinue` 可带 `files`：在同一队列里写入工作区并 `git add`，再用 `-c core.editor=true` + `GIT_EDITOR=true` 继续。`mergeAbort` / `rebaseAbort` 清掉进行中的操作。网页状态页告警条接 continue / abort（含拣选）。**禁止**用 `git_apply_resolve` 收尾工作区冲突；**禁止**用预演工具冒充 continue。
- **分支图 lineage**：`getBranchGraph({ into, from })` 在 tip DAG 之外算 `merge-base` 与两侧 `rev-list --count`；无关历史则 `mergeBase` 为空。网页选 into/from 点「对比」后，有共同祖先时 G6 画三节点 Y 图（分叉点 / 线上 / 我的）。

### 6.5 权限模型

`TOOL_RISK_LEVELS` 将工具分为 `readonly` / `write` / `dangerous`。已注册 Capability 时 `PermissionManager` 读 registry 的 `risk`；未注册（core 单测）回退本表。

`evaluate(tool)`：

1. 在 `disabledTools` → 不允许；dangerous 时 `requiredApproval=true`（提示去设置打开该工具）。
2. 否则允许。

MCP 的 write / dangerous 真执行前，必须有一次相同参数的成功干跑（内存票据，10 分钟，用一次）。`next[]` 不给出 `dryRun: false`。网页确认框和聊天确认令牌仍走各自的门。

**没有运行时人工点批准的队列**：「审批」= 管理员从配置里去掉该工具的审批/禁用项。Web 设置页 `PUT /api/settings` 可更新 `permissions`、`git.allowedRepos` 与 `mr`（当前仓 `repoMethods`、`defaultRemote`、按 host upsert Token），当场写回 `config.json`。Token 在 snapshot / 审计中脱敏（非空才打 `[REDACTED]`，空串保持 `''`，避免设置页误以为还有 Token）；GET 不回明文，只暴露当前仓 `hosts[].tokenSet` / `tokenPreview`（掩码，且仅当前 hostname）、识别出的 host，以及可选的 `current.tokenStatus` / `cli.*.tokenStatus`（`validateToken=1` 或刚校验过的 PUT）。PUT 带新 Token 时先校验，无效不写入。

### 6.6 备份

高危真实执行前：

- 工作区不干净或有未跟踪 → `git stash push -u -m "git-cockpit backup {ts}"`；
- 尝试创建 `backup/pre-op-{timestamp}` 指向当前 HEAD（空仓库可能失败，忽略）。

`BackupManager.listBackups()` 列出 `backup/pre-op-*` 分支，以及说明匹配 `git-cockpit backup` 的 stash。不提供「reset --hard 一键回到备份」；网页「记录」卡片可检出备份分支、apply 备份 stash、按 reflog hash 检出（分离 HEAD）。`GET /api/repos/:id/backups`、`GET /api/repos/:id/reflog`；MCP：`git_backup_list`、`git_reflog`。

### 6.7 MCP 双传输

- **stdio**：一个 `McpServer` + `StdioServerTransport`，适合客户端拉起子进程。
- **Streamable HTTP**：`McpHttpHandler` 按 `mcp-session-id` 维护会话；无 session 的请求只接受 `initialize`（其余直接 400，避免留下未登记的 transport），新会话同时创建自己的 `McpSessionContext`。Fastify 已解析 body，必须把 `req.body` 传给 SDK，否则 initialize 无响应。transport 开 `enableDnsRebindingProtection` + `allowedHosts`，并设 `enableJsonResponse: true`（POST 回 `application/json`，不用 SSE 长连接，便于桥接与命令行调试）。`allowedHosts` 由 `buildAllowedHosts()` 组装：配置 host、`127.0.0.1`、`localhost`、`[::1]` 各自带端口与不带端口两种形态，再并入 `req.socket` 的真实 `localAddress/localPort`（随机端口、`0.0.0.0` 绑定时也能命中；攻击者可控的只有 Host 头，不会出现在 socket 端点里，防护不削弱）。
- **session 级仓库绑定**（`mcpSession.ts`）：每个 MCP session 有自己的 `McpSessionContext`。`git_repo_select({ repoId | repoPath | clear })` 绑定/切换/清除；此后省略仓库参数的工具使用该绑定，不再读全局“最近打开仓库”。显式传 `repoId/repoPath` 只影响单次调用。绑定仓库被删除或移出 `allowedRepos` 时明确报错，不静默回退。`git-cockpit://repo/current` 优先返回绑定仓库（带 `bound`/`scope`/`repoId` 字段），未绑定时才退回旧的 `getCurrent()`。
- **服务端主动通知**：`bindMcpNotifications()` 把 `eventBus` 的 `repo-changed` / `job-progress` 映射成 `notifications/resources/updated` 与 `notifications/message`（logging 能力已声明），已绑定的 session 只收自己仓库的事件；`server.server.onclose` 时移除监听。
- **stdio→HTTP 桥**（`mcpBridge.ts`）：`createMcpForwarder` 用无 session 的 `GET /mcp` 做预检（有效请求返回 400，但不创建 transport），逐条转发并跟踪 `Mcp-Session-Id`；有 30s 超时、最多 2 次重试、最大队列 100 和异常隔离（单条失败只回该条 JSON-RPC 错误，不打断后续消息）。initialize 后同时订阅 GET `/mcp` SSE，把服务端主动通知写回 stdout（连续失败 5 次即放弃，只影响通知不影响请求-响应）；关闭时发送 DELETE 清理 session。
- 工具注册必须 `server.registerTool.bind(server)`，否则 SDK 丢失 `this` 导致握手挂起。Prompt / Resource 同样 `bind` 后注册。
- 服务端 `instructions`（与项目 `.cursor/rules/git-cockpit-mcp.mdc` 及 README「Agent 该怎么用」同口径）：先 `git_status`（`operation` 为 merge/rebase 时走工作区收尾）；写操作先 `dry_run=true`；高风险默认禁用；预演只用 merge-tree（`into`/`from`）；落盘用 `git_apply_resolve`；工作区冲突用 continue/abort；更新跟踪分支用 `git_fetch`；两分支分叉用 `git_branch_graph` 带 `into`/`from`。提交 / 预演落盘 / 工作区收尾 / 开 PR 用 Prompt；仓库列表与任务可读 Resource。

### 6.9 前端状态同步

1. `App.vue` 启动：health → 拉仓库列表 → `branches.load()` → 订 SSE。换仓库或 revision 变化时再拉分支列表（请求去重）。
2. SSE 到达 → `useRevision().bump()` → Status / Logs `watch(revision)` 刷新；合并页若已有调查结果则标「矩阵可能过期」（不自动重跑）。Agent / MCP 不订 `/api/events`；MCP session 通过 `/mcp` GET SSE 接收资源更新与日志通知。
3. 当前仓库：`localStorage git-cockpit:currentRepoId` 优先，否则卡片顺序第一项。
4. 分支数据：`useBranchesStore` 一份扁平列表；状态页工作区左树、合并页树选、提交面板「指定分支」共用，页面只做 scope 过滤（本地 / 远程 / 全部）。合并页单对与矩阵共用 `useMergeSessionStore`，切模式不丢调查结果与冲突队列。
5. 后台任务：`useJobsStore` 订 SSE `job-progress`，`chunk` 按 `\n`/`\r` 拆行追加；收到 `ok`/`error` 再拉详情并 Notification。底栏「任务」显示进行中数量。克隆成功后打开目标路径加入仓库列表。任务页左列表右日志，无抽屉；`?id=` 与左栏选中同步。

未落地的部署与安全项见本文 §13，此处不列规划清单。

### 8.2 安全机制摘要

- 三级工具 + 配置开关，无独立审批工单系统。
- 写操作 dry-run 返回 `{ dryRun, command, args, affectedFiles, risk, note }`。
- 高危自动备份见 6.6。
- 日志：时间、source、工具、仓库路径、脱敏参数、结果、耗时、是否 dry-run。

## 9. 数据与配置

数据目录默认 `~/.git-cockpit`（`GIT_COCKPIT_DATA_DIR` / `storage.dataDir`）：

| 文件             | 内容                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------- |
| `config.json`    | 服务端口、git 并发、权限、日志脱敏词、`mr.repoMethods`（按仓库路径的开单方式）、`mr.hosts[]`（按 hostname 的 Token） |
| `git-cockpit.db` | `operations` 审计表、`opened_repos` 仓库列表、`jobs` 后台任务（clone / survey / fetch）                              |

配置合并：`DEFAULT_CONFIG` ← 文件 ← 构造期 overrides，再 `normalizeMrConfig`（旧 `githubToken`/`gitlabToken` 迁到 `hosts`；旧 `method: auto` 迁成 `browser`）。损坏的 JSON 不阻断启动。`PUT /api/settings` 允许改 `permissions`，以及按当前仓写 `repoMethods`、改 `defaultRemote`、按 host upsert 或删除。snapshot 中非空 Token 显示为 `[REDACTED]`，已清除的空 Token 保持 `''`。

默认权限（`packages/core/src/types.ts`）：

```json
{
  "server": { "port": 3000, "host": "localhost" },
  "storage": { "dataDir": "~/.git-cockpit" },
  "git": {
    "backupOnDangerousOps": true,
    "allowedRepos": []
  },
  "auth": { "localSecret": "<首次启动生成的 64 位十六进制>" },
  "permissions": {
    "disabledTools": ["git_reset_hard", "git_clean", "git_push_force", "git_branch_delete_force", "git_rebase"],
    "requireApprovalFor": [],
    "dryRunDefault": false
  },
  "logging": {
    "level": "info",
    "redact": ["password", "token", "authorization"]
  },
  "mr": {
    "method": "browser",
    "defaultRemote": "origin",
    "hosts": [],
    "repoMethods": {}
  }
}
```

`allowedRepos` 为空不限制；非空时打开仓库（Web / MCP `repoPath`）必须等于名单中某条路径，或位于其目录下，否则 `REPO_NOT_ALLOWED`。

每仓 GitService 内部队列串行（保护 index）。不再有 `git.maxConcurrentOperations`。

`auth.localSecret` 首次启动写成 64 位十六进制，存在 `config.json`。`GET /api/health` 不校验。其余 `/api` 与 `/mcp` 要请求头 `X-Git-Cockpit-Secret`。`GET /api/bootstrap` 只在没有 `Origin` 时返回密钥，不给跨站页面。开发时 Vite 代理从 `config.json` 注入该头。设置页可复制。能读到 `config.json` 的本机进程不受这道头保护。stdio 不校验密钥：若本机 daemon 已经健康，`git-cockpit mcp` 转为**转发**到 `/mcp`（密钥由桥进程自己读配置注入，不落到客户端配置），预检失败则降级为独立 stdio。同一来源的 `GET /api/events`（浏览器 EventSource 带不了自定义头）在没有 `Origin` 时放行。

## 11. 部署与发布

### 11.1 命名与发布标识

| 标识       | 名称                                  | 说明                                                  |
| ---------- | ------------------------------------- | ----------------------------------------------------- |
| 产品展示名 | **Git Cockpit**                       | 与 Git Insight 形成「Insight 负责看、Cockpit 负责开」 |
| npm 主包   | `@shaohui_jin/git-cockpit-mcp-server` | MCP + Web + CLI；内嵌 `dist/web`                      |
| npm 核心包 | `@shaohui_jin/git-cockpit-core`       | 运行时依赖，供下游复用                                |
| CLI bin    | `git-cockpit`                         | 亦可 `git cockpit …`                                  |
| web 包     | `@shaohui_jin/git-cockpit-web`        | **不发布**，构建产物打进 mcp-server                   |
| 本地数据   | `~/.git-cockpit/`                     | 配置 + SQLite                                         |

当前版本在各 `package.json` 维护（例如 0.1.17）；core 与 mcp-server **版本号独立**。`GET /api/health`、MCP 握手、OpenAPI `info.version` 都读 mcp-server 的 `package.json`，不再手写。

### 11.2 本地使用

```bash
npm install -g @shaohui_jin/git-cockpit-mcp-server
git-cockpit start
# Web:  http://localhost:3000
# MCP:  http://localhost:3000/mcp
```

Cursor / Claude Desktop：

- stdio：`{ "command": "git-cockpit", "args": ["mcp"] }`（推荐；已有 daemon 时转发，没有时由该命令启动，客户端配置里不用写密钥）
- HTTP：`{ "url": "http://localhost:3000/mcp", "headers": { "X-Git-Cockpit-Secret": "…" } }`

两种方式指向同一个后端，可以混用（Cursor 走 HTTP、Claude Desktop 走 stdio，共用一份队列）。`git-cockpit mcp --standalone` 是显式逃生舱：本进程自建后端，多个客户端将各持一份队列与仓库锁，一般不需要。

多仓库场景下，MCP 客户端先读 `git-cockpit://repos`，再 `git_repo_select({ repoId })` 绑定 session；这样两个客户端同时用不同仓库时不会串仓。Agent 按哪四件事调工具，以仓库根 [README.md](../README.md)「Agent 该怎么用」为准（提交 / 预演落盘 / 工作区收尾 / 开 PR），不要只靠本仓库 Cursor rule。不要和 Git Insight MCP 同时用于同一仓。

开发（仓库根目录）：

```bash
pnpm install && pnpm build
pnpm start
# Web:       http://localhost:5173（Vite）
# API / MCP: http://localhost:3000
# API 文档:  http://localhost:3000/docs
```

`prestart` 会先构建 core 与 mcp-server；`start` 并行拉起 daemon 与 Vite。亦可：

```bash
node packages/mcp-server/dist/cli-entry.js start
# 另开终端：pnpm --filter @shaohui_jin/git-cockpit-web dev
```

### 11.3 npm 发布（与代码一致）

发布自动化在 **单个** `.github/workflows/release.yml`（两个 job，`release-mcp-server` `needs: release-core`），**不是**历史上的两个独立 workflow。

| 包         | tag                     | 判据                    |
| ---------- | ----------------------- | ----------------------- |
| core       | `core-v{version}`       | 远程无此 tag 才 publish |
| mcp-server | `mcp-server-v{version}` | 同上                    |

设计要点：

- **tag 在 publish 成功之后才推送**，表示「已发布」而非「试过了」；失败可原样重跑，不浪费版本号。
- 必须 `pnpm publish`：只有 pnpm 会把 `workspace:^` 改成真实 semver。
- mcp-server job 会先 **build core**（全新 checkout 无 `dist`），再 build web，再 publish mcp-server（`prepublishOnly` 复制 `dist/web`）。
- 因 job 顺序保证 core 先发，**不再**在 mcp-server 内轮询 `npm view`。
- 触发：push `master`/`main` 或 `workflow_dispatch`。Secret：`NPM_TOKEN`。
- core `0.x` 的 caret（如 `^0.1.0`）只覆盖 0.1.x；core 升 minor 时需同步 mcp-server 依赖范围。

core 构建后 `postbuild.mjs` 把 esbuild 剥掉的 `from "sqlite"` 改回 `from "node:sqlite"`。

失败重试、本地 dry-run 核对 tarball、镜像延迟等细节见 [release.md](./release.md)。

当前按本地单用户 daemon 设计，默认 `host=localhost`。远程多租户不在已实现范围内。

## 12. 注意事项与开发关键点

1. **唯一后端**：多客户端共用一个后端。`git-cockpit mcp` 已有 daemon 时转发到它，没有 daemon 时由当前命令启动并桥接；已有 daemon 但桥接失败不会再自动生成第二套 Runtime。MCP session 通过 `git_repo_select({ repoId })` 绑定自己的仓库上下文，避免多个客户端共享“最近打开仓库”。
2. **写操作收口**：新工具写进 `core/capabilities/git/*.ts` + GitService 方法，不要只写在 mcp-server，也不要在 Web 路由里直接调 git。
3. **只读 REST 无审计**：若需要「谁看过 diff」审计，应改为走 executeTool 或补日志。
4. **打包**：core 必须 external `node:sqlite` 并跑 postbuild；mcp-server 必须 shebang（`cli-entry.js`），且 core/SDK/fastify/zod 不 bundle。
5. **静态资源**：发布包靠 `dist/web`；源码开发靠 `packages/web/dist` 或 Vite 代理。
6. **Windows**：bin 无扩展名 + shebang，Git for Windows 才能找到 `git cockpit`；纯 `.cmd` 不会被 git 的 PATH 查找命中。
7. **体验**：无仓库时禁用写按钮；远程操作失败用 GitOperationError 友好文案（如「请先拉取」）。

## 15. 总结

Git Cockpit 把 **MCP 工具、Web API、CLI** 收束到同一套 `Runtime` + `executeTool` + `GitService`。宿主聊天窗口里的 Agent 与网页点按钮走同一套权限、预览、备份和审计。底栏干活（已配模型 Key 时聊天更靠前，否则排在合并后）与系统（任务 / 操作日志 / 设置）分开；聊天从底栏升起 overlay。提交在状态页第三档，没有独立历史页。合并预演不碰工作区；多分支可矩阵扫描并建议合入顺序；从矩阵选边只记本地临时分支，回矩阵再推送、开 MR；合并页单对仍可落盘并推送。落盘走独立 worktree。工作区已经冲突时用 continue/abort，不用 `git_apply_resolve`。状态页可看 tip DAG 与两分支 lineage、按路径树看更改、做日常写操作并回看备份/reflog；后台任务左右分栏看日志并可取消克隆。Insight 能力迁入已完成（下架不做）。本产品不内置对话模型。发版以 tag-after-publish 的单 workflow 为准。尚未落地事实见本文 §13。
