# 设计需求摘要 · 工作台（Dashboard）重设计

> 需求发现分析师：许明需（xu-mingxu）· Phase 1 产出
> 唯一事实源：`packages/web/src/views/ReposView.vue`、`packages/web/src/components/RepoCard.vue`、`packages/web/src/utils/repoAttention.ts`、`packages/web/src/stores/repos.ts`
> 用户输入：生产截图（20 仓：全部 20 / 雷雨 14 / 薄雾 3 / 刮风 0 / 晴天 3，雷雨中绝大多数显示「丢失 / 不可用」）+ 对上一版设计稿的四条否决意见

## 一、五要素

| 维度 | 结论 |
|------|------|
| 场景 | Git Cockpit 首屏「工作台」：已打开仓库列表 + 分诊 + 进入仓库的入口页 |
| 受众 | 开发者本人：同时维护 20 个仓库，每天开机第一眼就是这页，要快速判断「今天该动哪个仓」 |
| 调性 | 暗色驾驶舱工具风，信息密度优先；颜色是分诊信号而非装饰；沿用 gc 令牌体系 |
| 品牌上下文 | 设计体系完备（tokens.css / chrome.css），但上一版 dashboard.html 被否决：美感不足、为了设计而设计、没看懂业务。本次以生产功能与真实数据形态为唯一事实源 |
| 规模 | 单页高保真原型；需覆盖 20 仓真实规模、14 雷雨（多为丢失）的真实状态分布；静态原型 + 必要 JS 交互（筛选/折叠/菜单） |

## 二、真实业务场景分析（这是上一版设计稿最缺的部分）

### 2.1 数据形态：20 仓、14 雷雨、且雷雨多为「丢失」

- 工作台展示的是 `OpenedRepo[]`（最近打开过的本地仓库，按用户拖拽的 pinOrder 排序），**20 个是长期积累的常态规模**，不是 6 个。
- 天气由 `attentionOf()` 判定，规则顺序（生产代码事实）：
  1. `!overview || available === false` → **stuck（雷雨）**——即「路径不存在 / 不是 Git 仓库」的**丢失仓**
  2. `operation !== 'none' || conflictCount > 0` → stuck（真正「卡住」的活仓）
  3. `dirtyCount > 0` → dirty（薄雾）
  4. `ahead + behind > 0 || tempMergeBranchCount > 0` → sync（刮风）
  5. 其余 → quiet（晴天）
- **关键结论：雷雨是一个被污染的档位**。14 个雷雨里绝大多数是丢失仓（PropStudio、LayoutStudio、UIModule、AppCommon、XTCommon、SchemaStudio、ParamStudio、HarvestStudio、DramStudio、CustomStudio、Application、domain 等），真正「卡住」的活仓可能只有 0–2 个。用户看到「雷雨 14」的第一反应是「14 个仓出事了」，实际是「14 个仓的路径失效了」——**语义误导**，且丢失仓点进去只会报错（进入工作区/预演合并被禁用），雷雨档不可操作。
- 薄雾 3 = 有未提交更改，是用户**当天要干活的仓**。晴天 3 = 干净可开工。刮风 0 = 当前无人超前/落后。
- **真实可行动集合 ≈ 3–6 个仓，其余 14 个是死条目**。工作台的核心矛盾是：屏幕被 70% 的死条目占据，用户每天真正要找的 3 个活仓被淹没。

### 2.2 用户每天的使用流程（打开 → 分诊 → 进入）

1. **打开**：应用启动，工作台是首屏（无独立首页）。扫一眼页面即完成「今天有哪些活」的认知。
2. **分诊**：三件事——① 哪些仓有未提交更改/冲突（要动手）；② 哪些仓该同步（fetch/pull）；③ 哪些条目已失效（该清理）。当前用天气筛选完成，但雷雨档语义被丢失仓污染。
3. **进入**：点卡片切换当前仓 → 「进入工作区」进状态页，或「预演合并」进合并页。这是最高频的路径，必须 ≤2 步。
4. **低频维护**：打开新仓（输入路径 / 克隆）、单仓 fetch、移除条目、拖拽排序。

### 2.3 上一版设计稿为什么「没看懂业务」（逐条验证主理人诊断）

| 设计稿做法 | 与真实业务的冲突 | 结论 |
|---|---|---|
| attention 三联（20 里挑 3 个展示） | 选取武断；与天气筛选信息重复；20 仓里挑 3 个对分诊毫无帮助 | 确认：需重构为「可操作的待办聚合」而非展示位 |
| hero 当前仓大卡 | 与网格中当前仓高亮重复；首屏黄金位置被一个已知信息占用 | 确认：当前仓用网格高亮 + 紧凑操作条即可 |
| 5 个大天气卡（占首屏 1/5 高） | 每卡只有数字 + 天气名 + 一行 hint，信息密度极低；5 卡占 1/5 首屏，挤压网格 | 确认：降级为单行紧凑筛选条/chips |
| 6 卡稀疏网格 | 真实 20 仓一屏看不完；卡片高度 ~140px，一屏仅 2 行；分诊效率低 | 确认：必须提密度（紧凑卡）并处理丢失仓 |
| 无丢失仓概念 | 14 个死条目在网格里与活仓同权展示，点进去全部报错 | 新增需求：丢失仓一等公民设计 |

## 三、信息优先级（20 仓一屏扫读）

判定标准：这条信息能否帮用户在 3 秒内回答「这个仓要不要我动手？」。不能的，降级或移除。

| 优先级 | 信息 | 生产字段 | 处置建议 |
|---|---|---|---|
| P0 必须在卡上 | 仓名（身份） | `overview.name` / `repo.path` 末段 | 保留，mono，单行省略 |
| P0 必须在卡上 | 可用性 + 状态（丢失 / 冲突 / 操作未完成 / 有更改 / 待同步 / 干净） | `available`、`operation`、`conflictCount`、`dirtyCount`、`ahead`、`behind` | 保留，但**丢失必须与卡住视觉区分**（见第四节）；颜色只用于需要行动的仓 |
| P0 必须在卡上 | 当前分支 | `overview.current` | 保留，mono 单行省略 |
| P0 必须在卡上 | 需要行动的量化（N 更改 / N 冲突 / operation） | `dirtyCount` / `conflictCount` / `operation` | 保留，仅 >0 时显示，0 值不渲染 |
| P0 必须在卡上 | ⋯ 菜单入口 | — | 保留 |
| P1 有值时突出 | ahead/behind | `ahead` / `behind` | 保留但压缩：仅 >0 时着色显示（`3↑` / `2↓`），全 0 时合并为一个中性 `—` 或省略 |
| P1 有值时显示 | 合并草稿数 | `tempMergeBranchCount` | 仅 >0 时显示 chip |
| P2 可降级 | 打开时间 | `repo.lastOpenedAt` | 对分诊无价值；降级为 hover title 或移除 |
| P2 可降级 | 12 周活跃热力点阵 | `activity` / `activityStart` / `activityTotal` | **20 卡同屏时是纯噪音且占卡高**；建议移除或降级为单点「近 12 周活跃」小标记；如需保留，只能作为极低对比度底纹 |
| P2 可降级 | 当前仓完整路径 | `current.path` | 保留在 title/hover，条上可省略或截断 |

**卡片目标形态（需求级，非最终视觉）**：紧凑卡 ≤ 3 行——① 名 + 状态点/chip + ⋯；② 分支 + 更改/冲突量化；③（可选）同步/草稿。目标卡高 ~72–88px，300px 列宽下每行 4 张、1440 视口内容区一屏 3 行 ≈ 12 张。

## 四、丢失 / 不可用仓的处理需求（最大的一块）

现状问题：丢失仓 = `available === false`，被 `attentionOf` 归入 stuck，与「真卡住」混计为雷雨；卡片仅显示「丢失」「不可用」，前三项菜单禁用，只能移除。14 个死条目占据主网格，是工作台最大的体验债。

**需求（一等公民）**：

1. **语义拆档**：丢失 ≠ 卡住。天气/筛选语义上必须把「路径失效」从「雷雨」中剥离。建议保留现有 5 档筛选标签与 aria 文案不变（e2e 契约：`卡住 N` / `有更改 N` / `未同步 N` / `晴天 N` / `全部 N`），但**雷雨档计数只算真卡住的活仓**；丢失仓进入独立的「失效」分组（网格下方折叠区或独立折叠组），不占活仓网格。
2. **视觉标识**：丢失卡整体降饱和（muted），状态 chip 显示「丢失」（红弱底或中性灰），分支位显示「不可用」；卡上不显示任何同步/热力/打开时间等无意义数据（这些字段对丢失仓全是空的）。
3. **批量治理入口**：折叠区头部给出一行摘要 + 批量操作，例如「14 个仓库路径已失效 · 全部移除」；单卡 ⋯ 菜单仍可「移除（不删磁盘）」，确认弹窗沿用生产文案 `确定从列表移除 {path}？注意：不会删除磁盘上的仓库文件。`。**不虚构「重新定位路径 / relink」功能**——生产没有，若要引导用户重新打开，只能提供「重新打开」入口复用打开栏。
4. **操作禁用**：丢失仓的「进入工作区 / 预演合并 / 抓取这一仓远程」保持禁用（生产行为），原型中体现 disabled 态与提示文案 `路径不存在或不是 Git 仓库，不能进入工作区`（同类文案按动作变化）。
5. **计数诚实**：分诊摘要/筛选计数必须真实反映「活仓几个、失效几个」，不允许把失效混入「雷雨」造成「14 个仓出事」的误读。

## 六、设计约束

1. **密度**：1440×900 视口、内容区 ~1280px 宽，**一屏 ≥12 张卡**（4 列 × 3 行，卡高 ≤88px）；活仓（薄雾 + 晴天 + 刮风，本例 6 个）必须一屏全见、零滚动；20 仓（含失效折叠区）目标 ≤2 屏。
2. **视觉噪音**：晴天/干净仓**不得有任何彩色装饰**（无彩色左边条、无彩色 chip、无彩色图标），只保留中性灰文字与分隔；颜色只给「需要行动」的仓：雷雨红、薄雾琥珀、刮风青、失效降饱和灰。同一屏彩色元素（彩色 chip + 左边条 + 图标）总数受控，禁止「每张卡都带彩色」。
3. **分诊路径**：从看到问题到进入仓库 ≤2 步（点卡 → 进入工作区；或双击直入）；批量动作（移除全部失效 / fetch 全部）≤2 步且有确认。
4. **语义诚实**：计数必须真实（活仓数、失效数分开）；雷雨档不再混入失效仓；所有文案与字段来自生产，禁止虚构（无 relink、无 AI 建议、无虚构统计）。
5. **e2e 契约**（后续生产落地时）：`.repo-card`、`.el-switch` 无关、天气按钮文案含「有更改」、heading `工作台`、`filterAriaName` 五档 aria 文案均不得改；新增「失效」分组/折叠区不能移除原有 5 个筛选按钮。
6. **布局宽度**：工作台上限 1280px；网格 minmax 可调但仓名不得大面积截断（mono 单行省略可接受）；卡片内不出现横向滚动。
7. **审美纪律**（回应「为了设计而设计」）：每个视觉元素必须回答「它是否让分诊更快」；禁止 hero 大块、禁止重复展示同一信息（当前仓条与网格高亮二选一或明确分工）、禁止纯装饰性图形（热力点阵、渐变、发光仅限信号件）。

## 七、验收标准（用户看到什么算「看懂了业务」）

1. **第一眼可答**：打开原型 3 秒内能回答——我有哪些活仓、哪些需要动手、哪些是死条目。
2. **规模诚实**：20 仓真实规模渲染，一屏 ≥12 张卡；6 个活仓一屏全见；失效仓不混在活仓网格中。
3. **丢失仓一等公民**：失效仓有独立分组/折叠区 + 批量移除入口 + 视觉降饱和 + 操作禁用态；雷雨计数不再包含失效仓（或明确拆分为「卡住 / 失效」两个数）。
4. **噪音受控**：干净仓无彩色装饰；彩色仅标记需要行动的仓；无 hero、无 5 大卡、无重复信息块。
5. **路径高效**：点卡 → 进入工作区 ≤2 步；批量操作 ≤2 步。
6. **功能零丢失**：第五节「核心」项 100% 覆盖；可降级项能力仍在；文案与生产一致，零虚构。
7. **流程合规**：原型落在 docs/visual-refresh/ 供审阅，审阅通过前不改生产代码。

## 八、推荐方向（供设计系统专家定稿）

- 页面骨架建议：紧凑工具栏（打开/克隆/刷新 + 分诊摘要「6 活仓 · 3 待处理 · 14 失效」）→ 单行筛选条（5 档 chips + 失效档/折叠）→ 活仓紧凑网格（当前仓高亮 + 顶部紧凑操作条）→ 失效仓折叠区（摘要 + 批量移除）→ 空态/离线告警。
- 天气体系保留但语义校正：雷雨 = 真卡住（operation/conflict），失效 = 独立档位/分组；5 档筛选标签与 aria 不动。
- attention 能力改为「分诊摘要 + 可展开待办清单」，不再固定占三张卡位。
- 卡片去掉热力点阵与打开时间，压缩到 3 行；ahead/behind 仅非零着色。
- 工作台与设置页共用同一套 gc 令牌与 chrome；不引入新设计语言。
