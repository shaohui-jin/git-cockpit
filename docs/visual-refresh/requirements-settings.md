# 设计需求摘要 · 设置页重设计

> 需求发现分析师：许明需（xu-mingxu）· Phase 1 产出
> 唯一事实源：`packages/web/src/views/SettingsView.vue` + `packages/web/src/components/MrTemplateSettings.vue`（生产代码）
> 设计体系：`docs/visual-refresh/assets/tokens.css` + `chrome.css`（--gc-* 令牌）

## 一、五要素

| 维度 | 结论 |
|------|------|
| 场景 | 桌面 Electron 应用「Git Cockpit」的**设置页**，四 tab 结构（MR 配置 / 正文规范 / 模型 / Git 操作），改造为可切换 tab 的高保真 HTML 原型，供用户审阅后再改生产 |
| 受众 | 开发者本人（技术素养高，日常使用本机 Git 驾驶舱）；信息密度优先，不是营销页 |
| 调性 | 暗色驾驶舱工具风：深蓝黑三分层表面 + teal 签名主色（已定稿，极地白留档）、等宽字体用于路径/Token/host、禁渐变、圆角 ≤10px、发光仅限信号件。沿用现有 gc 令牌体系，不引入第二套设计语言 |
| 品牌上下文 | 已有完整设计体系（tokens.css / chrome.css）与 7 页原型；但现有 `settings.html` 原型是「5 张卡片、无 tab」结构，与生产四 tab 信息架构**货不对板**，且含虚构功能（重新生成密钥、连接测试、审计日志、自动升级、claude 模型等生产中不存在）。本次以**生产功能为唯一事实源**重做原型 |
| 规模 | 单页四 tab 全量重设计；静态高保真原型（可 tab 切换、可展示关键状态态），不含真实数据请求；后续落地时才接生产 |

## 二、生产实际功能清单（原型必须 1:1 覆盖，允许丢功能即不通过）

> 以下字段、控件、状态文案、按钮文案均逐字取自生产代码。原型中出现的每个文案都必须能在这张清单里找到出处。

### 2.0 页面公共部分

- 页头：`设置`（h1）+ 副题 `本机保存，不上传`；右侧 chip（mono）：`服务 {版本号}`
- 全局错误：settings.error 存在时，页面顶部一条 error alert（不可关闭、带图标）
- Tab 栏（gc-chip-tabs，四个按钮，当前项高亮，顺序固定）：`MR 配置`（默认选中）/ `正文规范` / `模型` / `Git 操作`。tab 状态写入 URL query（mr 为默认无 query）
- 切回 MR 配置 tab 时会触发一次带 Token 校验的刷新（原型需体现 MR tab 的加载态）

### 2.1 Tab「MR 配置」（默认 tab，结构最重）

**卡片 1 · 默认远程**（card-head：remote 图标 + `默认远程` + 右侧平台 tag：`GitHub` / `GitLab` / `未识别`）

- 有 remote 时：远程名下拉选择（切换后**立即保存**）+ 右侧 mono 显示远程 URL（超长省略）
- 无 remote 时两种空态文案：
  - 已选仓库：`当前仓库没有 remote`
  - 未选仓库：`未选择仓库，请先在工作台打开仓库`
- 底部说明（fhint）：`用于 fetch、MR 短名剥前缀、CLI 未传远程时的默认值。切换后立即保存。`
- 附加行（仅 platform 未识别且有 remote 时）：提示 `未能自动识别远程平台，请手动选择。` + `GitHub` / `GitLab` 两个按钮

**MR 方式三张可选卡片**（整卡可点击、可键盘 Enter；选中态：accent 弱底 + 1px accent 内边；每卡头部右侧状态文字：`可用`（绿）/ `未就绪`（红））

- 卡片 A 标题随平台变化：`A. 本机已安装的 gh`（GitHub）/ `A. 本机已安装的 glab`（GitLab）/ `A. 本机已安装的 gh / glab`（未识别）
  - 展开面板内容：gh 行（mono `gh` + 状态 + 动作）；glab 行（仅非 GitHub 平台显示）
  - CLI 状态三态：`未下载`（附 `去下载` 外链）/ `未登录` / `已登录`（已登录且带校验结果时，显示彩色状态文字，ok 绿 / bad 红）
  - 面板底部：`重新检测` 按钮（成功后提示 `已重新检测本机 gh / glab`）
- 卡片 B 标题带 host：`B. Token（API）`（无 host）/ `B. GitHub Token（{host}）` / `B. GitLab Token（{host}）`
  - 无 host 空态两种：`当前仓库没有可识别的远程地址，无法绑定 Token。` / `请先在工作台打开并选择仓库。Token 始终绑定当前远程的域名。`
  - 有 host 时表单（标签 `Token`）：
    - 状态行：`校验中…` / 已保存 Token 的校验结果文字（ok 绿 / bad 红 / 无结果 muted）
    - 密码输入（可显示明文），placeholder 三态：`已保存 {preview}，明文不回填，输入新 Token 覆盖` / `ghp_… 或 github_pat_…` / `glpat-…`；platform 未识别或校验中禁用
    - 说明文字按平台：`需 repo 权限。Token 不进工具参数。`（GitHub）/ `审核人用户名会解析成数字 id。Token 不进工具参数。`（GitLab）/ `Token 不进工具参数。`（未识别）
    - 链接行：`打开 GitHub 创建 Token 页面`（非 GitLab 时）/ `打开 GitLab 创建 Token 页面`（非 GitHub 时）/ `自建 / API Base URL` 展开收起切换
    - 展开后：`API Base URL` 输入，placeholder `空则按域名惯例推断，如 https://git.a.com/api/v4`
    - 按钮行：`保存此远程配置`（主按钮，无修改或校验中禁用，含 loading）/ `重新校验`（未保存过 Token / 有未保存修改 / 校验中时禁用）/ `放弃修改`（无修改时禁用）
- 卡片 C：`C. 仅打开浏览器创建页`（始终可用）
  - 面板提示：`确认后只返回浏览器创建页，不调用 Token 或本机 CLI。`；已启用正文规范时追加：`已启用正文规范时，平台创建页不会写入正文，请复制后粘贴，或改用 Token / 本机 CLI。`

**卡片 2 · 当前远程凭证**（仅当前远程能识别出 host 时出现）

- card-head：key 图标 + `当前远程凭证` + 平台 chip（`GitHub` / `GitLab`）
- 说明：`只显示当前选中远程的域名。其它实例上的 Token 不在这里列出。`
- 行：mono host + tag（`已配置 Token` 带 preview / `无 Token`）+ `清除` 危险文字按钮（确认弹窗：`清除 {host} 上保存的 Token 与覆盖项？`，按钮 `清除` / `取消`）

### 2.2 Tab「正文规范」（用户痛点 1 的主战场，功能最密集）

外层为一张带边框卡片，内部分**头部两行 + 粘贴栏 + 双 pane**：

**头部行 1（状态与控制）**

- 状态 tag 三态：`已启用`（绿）/ `已导入未启用`（灰）/ `未导入`（灰）
- 开关：`启用规范`（el-switch；没有可填写字段时禁用）
- 单选组：`允许 AI 填写` / `须人工填写`（没有可填写字段时禁用）
- 右侧 mono 显示导入的文件名（如 `pasted.md`）

**头部行 2（操作按钮）**

- `导入 Markdown`（触发隐藏文件选择，accept `.md/.markdown/text/markdown/text/plain`，解析中 loading）
- `粘贴导入`（切换粘贴栏显隐）
- `保存规范`（主按钮，有修改时才可点，保存中 loading）
- `放弃修改`（有修改时才可点）
- `清除`（从未保存过时禁用；确认弹窗 `清除已保存的正文规范？未启用时开单行为与现在相同。`）

**粘贴栏**（粘贴导入展开时）：4 行 textarea（placeholder `粘贴 MR 模板 Markdown`）+ `识别` 按钮；导入成功提示 `已识别 {N} 个模块，请校对后保存`

**双 pane（当前生产为上下堆叠，正是痛点 1）**

- 左 pane「结构」：头部 `结构` + `添加` 文字按钮
  - 空态：`还没有章节。导入一份 .md，或点右上角添加。`
  - 字段卡列表，每卡：
    - 头行：类型下拉（`多行文本` / `单选` / `勾选` / `说明（不填）`，宽 120px）+ 标题输入（placeholder `标题`）+ `必填` 勾选（说明类型时隐藏）+ mono 字段 id + `删除` 危险文字按钮
    - 非说明类型：说明 textarea 2 行（placeholder `说明（开单时给填写人看）`）
    - 多行文本：占位输入（placeholder `占位`）
    - 单选：选项行列表（输入 placeholder `选项` + `删`）+ `添加选项`；类型切换为单选时默认注入 `低 / 中 / 高` 三个选项
    - 勾选：条目行列表（输入 placeholder `条目` + `必勾` 勾选 + `删`）+ `添加条目`
    - 说明（不填）：说明正文 textarea 6 行（placeholder `说明正文`）
- 右 pane「预览」：头部 `预览` + `刷新` 文字按钮（无字段时禁用，刷新中 loading）
  - 有内容：pre 块展示渲染出的 MR 正文
  - 空态：`导入或修改字段后，这里显示渲染出的 MR 正文。`

**交互细节（原型需体现）**

- 草稿变更 400ms 防抖自动刷新预览；保存后刷新预览
- 导入成功且有可填字段时自动打开启用开关
- 删除字段后没有可填写字段时自动关闭启用开关
- 启用状态下保存但无可填写字段：警告 `没有可填写字段时不能启用规范`

## 三、三个用户痛点与对应设计约束

### 痛点 1：「正文规范和 git操作 横向会被压扁，纵向看不到内容很不合理」

- 根因：上一轮把两个双内容 pane（正文规范的 结构/预览、Git 操作的 默认行为/工具开关）从左右分栏改成了上下堆叠，塞进 880px 单列容器。两个 pane 都被压扁，且下方 pane 被折到折叠线以下，纵向看不到。
- **分栏 vs 堆叠判定规则（本次必须遵守）**：
  1. 设置页内容区不再死守 880px。tab 级自适应：单栏卡片 tab（MR 配置、模型）保持 ≤880px 居中；双 pane tab（正文规范、Git 操作）允许加宽至 ~1200px 或全宽，供左右分栏使用。
  2.  pane 最小舒适宽度：结构编辑器 ≥360px、预览 ≥360px、工具芯片墙 ≥600px（52 个芯片一行 4–6 个）、默认行为表单 ≥320px。左右分栏后每侧不得低于各自最小值。
  3. 判定优先级：**两个 pane 都完整可见且无需横向滚动 > 分栏形态**。若某视口下分栏必然压扁，则退化为「关键 pane 完整显示 + 次要 pane 独立滚动」，不允许两个 pane 同时残缺。
  4. 纵向「看不到内容」一票否决：任何 tab 的首屏必须完整露出该 tab 的主操作（正文规范的保存/导入/启用开关；Git 操作的保存按钮与工具墙首屏至少 3 组）。
- 具体形态（供设计系统专家定稿，二选一或融合）：
  - 方案甲：恢复左右分栏 + 内容区加宽（正文规范 结构 5 : 预览 7；Git 操作 表单 4 : 工具墙 6）。
  - 方案乙：保持堆叠但工具墙区独立滚动、纸面化分区。若选乙，必须保证上卡片不抢占下卡片首屏。

### 痛点 2：「git操作上面的表单，左边文本label占这么大一块，样式这么不合理」

- 根因：frow 模式（label 固定 140px 右对齐 + 控件）被套用在所有字段上。`允许打开的仓库`（6 行 textarea + 两行说明）、`本机访问密钥`（按钮 + 三行说明）这类「标签 + 大控件 + 长说明」字段上，140px 右对齐标签造成大量左侧空白、视觉失衡。
- **表单标签宽度方案（本次必须遵守）**：
  1. 标签列占位不得超过控件列的 1/3；短标签（≤5 个汉字/英文词，如 `模型名`、`Base URL`、`API Key`、`dry-run 默认`）可保留紧凑右对齐标签，宽度按该卡片最长标签定宽（建议 ≤96px）。
  2. 大控件 + 长说明字段（允许打开的仓库、本机访问密钥、正文规范的字段编辑卡）**标签上置左对齐**，标签与控件同宽起点，说明文字跟在控件下方——与设计稿 swrow（标题 + 说明 + 右侧开关）的思路一致。
  3. 全站标签宽度不强制统一数值，按卡片内字段构成决策；同一卡片内保持一致。
  4. 设计稿中 swrow（b 标题 + span 说明 + 右侧开关）优于生产 frow+switch 的表达，Git 操作的 `dry-run 默认` 行建议吸收该形态。

### 痛点 3：「首页的工作台也是跟设计稿货不对板」（工作台下轮处理；设置页先立规矩）

- 根因：设计稿 `settings.html` 是「5 张卡片、无 tab」结构，与生产四 tab 信息架构差异大；且设计稿虚构了生产中不存在的功能（重新生成密钥、连接测试、审计日志开关、自动升级服务、claude 模型下拉、MR 模板单 textarea + 变量 chips 等）。上一轮按着一个虚构结构改生产，必然货不对板。
- **与设计稿的一致性边界（本次必须遵守）**：
  1. **信息架构以生产为唯一事实源**：四 tab + 第二节功能清单，1:1 覆盖，不增不减不改文案。设计稿里的虚构功能一律不进原型。
  2. **视觉语言向设计稿对齐**：set-card 框架（card-head 36px / set-body / card-foot）、按钮与 chip、test-tag 三态、switch、暗色三层表面、teal 主色、mono 用于路径/Token/host、禁渐变、圆角 ≤6px、发光仅信号件。
  3. 可吸收的设计稿优点：swrow 开关行（痛点 2）、card-foot 的左侧状态文字位（如 `任务执行本身不消耗模型额度`）。
  4. 工作台不在本次范围，用户要求一件一件来；设置稿通过后才动生产代码。

## 四、验收标准（用户看到什么算过）

1. **功能全覆盖**：原型四个 tab 可切换，对照第二节清单逐项打勾，覆盖率 100%——真实字段名、真实状态文案、真实按钮文案、真实空态，零虚构、零丢失。
2. **痛点 1 通过**：正文规范与 Git 操作两个 tab 在 1280×800 与 1440×900 两档视口下，双 pane 均完整可见、无横向滚动；工具墙 52 个芯片按 10 组完整渲染；关键操作首屏可达。
3. **痛点 2 通过**：Git 操作默认行为卡片的标签不再占据过大宽度；大控件字段标签上置；用户明确指出不满的「label 占一大块」观感消除。
