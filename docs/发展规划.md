## 0. 为什么现在写这份文档

日常 Git、merge-tree 预演、三栏选边、worktree 落盘、矩阵/合入顺序、开 PR/MR、状态页 tip 图、后台克隆、权限/dry-run/备份/审计已经闭环。再堆 `git_*` 动词边际价值低。

下一阶段不是「功能清单补齐」，而是把已经写出来、但仍是专用实现的几条缝长开：

| 缝 | 现状 | 问题 |
|----|------|------|
| Agent 输出 | 工具很多，结果整包 JSON 丢给宿主 | 模型上下文被大 diff / 大 survey 吃光，编排靠口头 instructions |
| Job | `JobManager` / `clone_jobs` 只服务克隆 | 矩阵扫描、多仓 fetch、长预演没法走同一套「可取消 + SSE + 重启中断」 |
| 仓库页 | `/repos` = 打开 + 克隆 + 任务列表 + 路径树 | 多仓没有脉搏；任务和仓库管理叠在同一页 |
| 包边界 | core 已发 npm，但能力注册、安全链路、Job 执行仍散在 mcp-server | 加能力要改三处；下游复用的是「内部包外发」，不是能力层 |
| 产品化 | 能跑、能发 npm | 缺 E2E、缺首次引导、宿主侧说明只活在本仓库 rule 里 |

**产品身份不变**：脑子在宿主（Cursor / Claude 聊天窗口），手在 Cockpit（执行 / 预演 / 网页手选 / 落盘）。本产品不内置对话或选边模型。

## 1. 原则

1. **能走现有 `GitService` / `executeTool` 就必须走。** 禁止再开一条 git 通道。新能力先问：是新 kind 的 Job、新 Capability，还是只改结果形状。
2. **预演不碰工作区，落盘只用独立 worktree。** 这条楔子可以沿用到 cherry-pick / revert / worktree 管理；禁止用工作区 `git merge` 冒充预演。
3. **三个包、三种职责，不拆第四个包。** npm 仍是 core + mcp-server；web 私有、打进 mcp-server。daemon（Fastify + CLI）继续住在 mcp-server 里，不新开 `packages/daemon`。
4. **先加深已有面，再加新动词。** Agent 结果分层、通用 Job、工作台，优先于再注册一批 `git_*`。
5. **本机单用户 daemon 不放松。** 默认 `localhost`；不做远程多租户、不做扩展、不做网页 LLM。

### 1.1 明确不做

与设计文档 §13 对齐，规划期继续有效：

| 项 | 原因 |
|----|------|
| Cursor / VS Code 扩展 | 已拍板 |
| 网页 AI 选边、LLM 配置、Chat 桥 | 脑子在宿主 |
| 机械 resolver、冲突预警、选边/trail 入库 | 已拍板 |
| 多条 from 合成一条 `merge/batch-…` | 风险高；矩阵已能逐条推 |
| 下载 gh/glab 到本机 | 用户自装或用 Token |
| 远程 Docker 多租户 | 安全模型依赖本机进程 |
| 再做一套 Git GUI 去追 Fork / GitKraken | 稀释「安全 + 预演 + Agent」 |
| 为凑数加日常 `git_*`（bisect / submodule 全家桶等） | 缺的是编排和结果形状，不是动词 |

## 2. 包边界（能力层）

目标：每个包「能做什么 / 不能做什么」一眼能判。加功能时按表落文件，而不是看哪个目录顺手。

```
packages/core          能力：git 事实、权限、备份、审计、Job 引擎、Capability 注册与执行
packages/mcp-server    进程壳：CLI + Fastify REST/SSE/静态 + MCP SDK（tools / prompts / resources）
packages/web           瘦 UI：Vue 只调 REST，不碰 git / sqlite / MCP SDK
```

### 2.1 允许与禁止

| 包 | 允许 | 禁止 |
|----|------|------|
| **core** | `GitService` / merge-tree / survey / chain / blame / worktree 落盘；`PermissionManager`；`BackupManager`；`AuditLogger`；`RepoStore`；通用 `JobStore` + `JobEngine`；Capability 定义（name / risk / schema / handler / agent 输出策略）；MR 的 HTTP/CLI（git 做不到的平台事） | 依赖 `@modelcontextprotocol/sdk`、Fastify、Vue；在 handler 外再 spawn 一套 git |
| **mcp-server** | `git-cockpit start` / `mcp`；把 Capability 注册成 MCP tool；MCP prompts / resources；`formatResultForMcp`（文本包装）；Fastify 路由把 REST/SSE 接到 core；OpenAPI；`copy-web` 内嵌前端 | 解析 merge-tree、实现 survey/chain、自写 Job 进度协议、在路由里直接 `simpleGit()` |
| **web** | 视图 / Pinia / 路由 / G6 / 三栏 hunk；`useToolAction` 只打 REST；订 SSE | `import` core；拼 git 命令；自己算 merge-base / 冲突正文 |

`mcp-server` 名字容易理解成「只做 MCP」。实际它是**唯一进程壳**（Web 与 `/mcp` 必须同进程才能共享队列）。规划不改包名、不拆包；文档和 README 把「进程壳」写清楚即可。

### 2.2 Capability：工具定义下沉 core

现状：`TOOL_DEFS` 在 `packages/mcp-server/src/tools/index.ts`，`executeTool` 在同包 `handlers.ts`。Web `POST /tools/:tool` 与 MCP 共用，但定义住在「MCP 包」里，core 无法单独复用「带权限的能力」。

目标形态：

```
core
  capabilities/
    types.ts          Capability / CapabilityContext / ExecutionResult
    registry.ts       register + list + get
    executor.ts       现 executeTool 安全链路（权限 → zod → 解析仓库 → 备份 → handler → 审计）
    git/*.ts          按域拆：status / write / merge / mr / stash / dangerous
  jobs/
    types.ts
    store.ts          现 JobStore 泛化
    engine.ts         现 JobManager 泛化（取消 / 节流 SSE 事件 / 重启中断）
    kinds/clone.ts
    kinds/survey.ts   后期
    kinds/fetch.ts    后期

mcp-server
  tools/bindMcp.ts    遍历 registry → SDK registerTool
  tools/prompts.ts
  tools/resources.ts
  tools/format.ts     formatResultForMcp（摘要优先）
  webServer.ts        REST 调 executor / JobEngine
```

`CapabilityContext` 由进程壳注入（config / db / repo 解析 / eventBus），core 不认 Fastify Request。仓库解析优先级不变：`repoId` > 上下文 `repoPath` > `args.repoPath` > 最近打开。

**迁移策略**：先在 mcp-server 维持 `TOOL_DEFS` 再转调 core executor（避免一次大搬），再按域把 handler 移进 core。期间禁止新加工具只写在 mcp-server。

权限表 `TOOL_RISK_LEVELS` 改为从 registry 推导，避免「加工具改三处」。

### 2.3 判定顺序（写代码前）

规划期新代码也走这张表：

1. GitService 有没有现成方法？有 → Capability handler 只调它。
2. 是长任务（克隆、大矩阵、多仓 fetch）？→ 注册 Job kind，不要把同步工具调用卡死。
3. 只是给 Agent 少传点字？→ 改输出策略 / Resource，不要新工具名。
4. git 做不到（GitHub/GitLab HTTP、ssh→https）？→ 留在 core 的 `mr*` 模块，不塞进 GitService。

## 3. 给 Agent 用：加深设计

Cockpit 不调模型。加深的是：**工具更好调、结果更省、长任务可等、常见流程可复述**。

### 3.1 现状缺口

- MCP 只注册了 `tools`。无 prompts、无 resources。`instructions` 是一长段静态文本，宿主不一定每次都读全。
- `formatResultForMcp` 把整个 `result` `JSON.stringify`。`git_merge_rehearse` / `git_diff` / `git_merge_survey` 一次就能撑爆上下文。
- Agent 订不到 `/api/events`。克隆/长扫描只能瞎等或把同步调用打满超时。
- 没有「已打开仓库一览」工具。模型只能靠用户口头给 `repoPath`，或赌最近打开仓。
- 写操作建议先 `dry_run=true` 已写在 instructions 里，但成功结果没有「下一步该调哪个工具」的机器可读提示。

### 3.2 输出合同（所有只读大结果遵守）

工具结果分两层。默认只回摘要；正文按 path / job / resource 再取。

```json
{
  "ok": true,
  "summary": {
    "clean": false,
    "conflictCount": 3,
    "paths": ["src/a.ts", "src/b.ts", "pnpm-lock.yaml"],
    "hint": "先 git_merge_rehearse 带 path，再 git_apply_resolve"
  },
  "next": [
    { "tool": "git_merge_rehearse", "args": { "into": "origin/master", "from": "feat/x", "path": "src/a.ts" } }
  ],
  "detail": null,
  "detailAvailable": true,
  "jobId": null
}
```

规则：

| 规则 | 说明 |
|------|------|
| 默认 `detail` 为空 | `git_diff` / `git_show` / `git_merge_rehearse` / `git_file_content` 只回统计 + 路径 + 是否截断 |
| 显式要正文 | `detail=true` 或已有的 `path` / `maxFiles` / `maxPatchBytes`。单文件优先于整包 |
| survey 永不带正文 | 已是结论 + 路径；格子颜色仍不进 MCP |
| 写操作 dry-run | 维持现有 `WritePreview`（command / args / affectedFiles / risk / note），可附 `next` |
| 长任务 | 估时或规模超阈值时不塞满结果，回 `{ jobId, status: "running" }`，用 Job 工具/Resource 查 |

阈值（可配置，先写死默认）：

- rehearse 冲突文件 > 5 或单文件 diff3 > 64KB → 只回路径，请带 `path`
- survey 格子 > 20 或未完成 → 必须走 Job
- diff rawPatch 默认更小的 Agent 上限（例如 64KB），Web REST 可继续 2MB

`formatResultForMcp` 改成：失败一行；成功先打 `summary` 与 `next`，再视体积决定是否附 JSON。禁止把 2MB patch 当默认成功输出。

### 3.3 新增 / 调整的 MCP 面

**不新发明一套 Git。** 下列是编排面，或把已有 REST 事实暴露给宿主。

#### 只读工具

| 名称 | 作用 |
|------|------|
| `git_repo_overview` | 已打开仓库脉搏：路径、当前分支、脏文件数、ahead/behind、`operation`、本地 `merge/*` 条数、近 12 周提交总数。默认不含每日格子。不回 diff。工作台与 Agent 同源 |
| `git_job_list` / `git_job_get` | 后台任务摘要 / 详情（日志尾 + `result` 摘要） |

现有 `git_merge_preview` / `rehearse` / `survey` / `diff` / `show` 增加 `detail`（或收紧默认），schema 保持向后兼容：不传则摘要。

#### 写 / 任务工具

| 名称 | 作用 |
|------|------|
| `git_job_cancel` | 取消进行中任务（克隆杀进程；survey/fetch 合作式停） |
| 现有长工具可异步 | `git_merge_survey` 在格子数超阈值或 `async=true` 时返回 `jobId`，不阻塞 MCP 会话 |

克隆对 Agent 也走 Job：可新增 `git_clone`（write，URL 禁止 token，目标过 `allowedRepos`），内部只 `JobEngine.start('clone')`。没有该工具时，Agent 仍只能让人去网页点，保持现状也可以，**不作为第一期必做**。

#### MCP Prompts（playbook）

把本仓库 `.cursor/rules/git-cockpit-mcp.mdc` 的硬规则收成可调用 prompt，供宿主「插入工作流」，而不是只靠 server instructions。

| prompt | 何时用 | 关键步骤 |
|--------|--------|----------|
| `safe_commit` | 用户要提交 | `git_status` → `git_diff`（摘要）→ 按需 `git_add` dry_run → `git_commit` dry_run → 执行 |
| `merge_preview_apply` | 合不合得进去 / 要落盘 | 先看 `operation`；预演只用 preview/rehearse；into=ours / from=theirs；落盘只用 `git_apply_resolve` |
| `workspace_continue` | 工作区已在 merge/rebase | `git_status` → continue/abort；禁止 apply_resolve 收尾 |
| `open_mr` | 要开 PR/MR | `git_mr_prepare` → `git_mr_create`；Token 不进参数 |

Prompt 文本写死 into/from、禁止用 `git_merge` 冒充预演。不在 prompt 里教模型自动选边。

#### MCP Resources（拉状态，少占 tool 轮次）

| URI | 内容 |
|-----|------|
| `git-cockpit://repos` | 与 `git_repo_overview` 同摘要 |
| `git-cockpit://repo/current` | 最近打开仓的 status 摘要 |
| `git-cockpit://jobs` | 任务列表摘要 |
| `git-cockpit://jobs/{id}` | 单任务状态 + 日志尾 + result 摘要 |

Resources **只读、不进审计**（与现网只读 GET 一致）。写操作仍走 tool + executeTool。

Agent **不订 SSE**。长任务用 `git_job_get` 或读 Resource 轮询。以后若 SDK 会话通知稳定，再把 `job-progress` 转成 notification，不作为第一期。

### 3.4 宿主侧说明（产品的一部分）

本仓库 rule 继续给本仓开发用。对外要有一份可复制的「怎么配 MCP / 何时调哪些工具」：

- README「MCP 使用」补：HTTP 与 stdio 的推荐（多客户端用 `start` + `/mcp`）
- 短文或 README 小节：四条 playbook 的人话版（与 prompt 同口径）
- **不**做独立 Skill 包；Cockpit 只提供 MCP prompts + 文档

### 3.5 Agent 加深的验收

- 默认调用 `git_merge_rehearse`（无 `path`、多文件冲突）返回体积明显小于现在的整包 diff3
- 宿主能列出已打开仓库而不猜路径
- survey 超阈值返回 `jobId`，`git_job_get` 能看到完成/失败
- `safe_commit` / `merge_preview_apply` 两条 prompt 已注册，instructions 与 prompt 口径一致（into/from、预演/落盘/工作区收尾三分）

## 4. 通用后台任务（Job）

克隆已经证明：长任务需要「不占当前仓队列（或占但可取消）+ 进度 SSE + SQLite 落盘 + 重启标中断」。把它收成引擎，克隆变成第一种 kind。

### 4.1 模型

```ts
type JobStatus = 'running' | 'ok' | 'error';
type JobKind = 'clone' | 'survey' | 'fetch'; // 第一期这三种；其后按需加

interface Job {
  id: string;
  kind: JobKind;
  status: JobStatus;
  title: string;                 // 列表展示，如 "clone org/repo" / "survey 3×4"
  repoPath?: string;             // 有所属仓则填；clone 成功前为空
  repoId?: number;
  payload: Record<string, unknown>; // clone: { url, destDir }；survey: { intos, froms, fetch }
  logs: string[];
  result?: unknown;              // 完成时的摘要（survey 格子结论等）
  error?: string;
  progress?: { current: number; total: number; message?: string };
  startedAt: string;
  finishedAt?: string;
}
```

**kind 契约**（core 内注册，进程壳不写进度协议）：

| kind | 执行位置 | 取消 | 重启 |
|------|----------|------|------|
| `clone` | `spawn`，不进当前仓 GitService 队列（尚无仓） | 杀进程 + 删不完整目标目录 | `running` → `error`（「服务重启，任务中断」） |
| `survey` | 该仓 GitService **enqueue 一次**整批（已有「整批只 fetch 一次」） | 合作式：下一格前检查 abort；已算完的格子保留 | 同上，不把半套矩阵当成功 |
| `fetch` | 单仓 `git fetch` 进该仓队列；「多仓 fetch」= N 个 job 或一个 job 串/并行多 path | 合作式 | 同上 |

同一仓库：**最多一个**占该仓队列的 running job（survey/fetch）。clone 按目标目录互斥。跨仓库可并行（每仓一个 GitService）。

写操作落盘（`git_apply_resolve`）第一期 **保持同步工具**：单对通常秒级，矩阵逐条由人/Agent 调。不要把选边正文塞进 Job payload。

### 4.2 存储迁移

现表 `clone_jobs`（`url` / `dest_dir` 列是克隆专用）。迁移：

1. 新建 `jobs`：`id, kind, status, title, repo_path, repo_id, payload, logs, result, error, progress, started_at, finished_at`
2. 把已有 `clone_jobs` 行迁入：`kind='clone'`，`payload={url,destDir}`，`title` 用 url
3. 读库兼容：无 `jobs` 表时仍能读旧表（一个 migrate 版本号即可）
4. 保留最近约 30 条的策略不变，按 `started_at` 不按 kind

`JobEngine` 事件仍叫 `job-progress`，payload 带 `kind`，前端按 kind 渲染。节流约 200ms、结束补 `GET /api/jobs/:id` 的协议不变。

### 4.3 API / MCP

| 面 | 行为 |
|----|------|
| `POST /api/jobs` | `{ kind, payload }`，权限：clone 走现有校验；survey/fetch 要已打开仓且过 `allowedRepos` |
| `GET /api/jobs`、`GET /api/jobs/:id`、`POST /api/jobs/:id/cancel` | 与现克隆接口同形，列表摘要不含全量 logs |
| 兼容 | `POST /api/jobs/clone` 第一期保留，内部转 `kind=clone`；文档标 deprecated |
| MCP | `git_job_*`；survey 异步时只回 jobId |

审计：创建/取消记一条（source=web/mcp）；running 期间的 chunk **不**逐条进 `operations`。

### 4.4 进程壳与 core 的分工

- core：`JobStore`、`JobEngine.start/cancel/list/get`、kind runner、重启 `restore()`
- mcp-server：HTTP 路由、SSE 转发 `eventBus`、把 MCP 工具接到 Engine
- web：`useJobsStore` 按 `kind` 显示标题；抽屉日志通用，不写死「克隆日志」

### 4.5 Job 验收

- 克隆行为与现网一致（进度、取消、重启中断、成功后 open）
- survey 20+ 格可 `async` 跑完，页面与 `git_job_get` 都能看到格子结论
- 同仓不能同时跑两个 survey；clone 与他仓 survey 可并行
- 表迁移后旧 `clone_jobs` 能在列表里看到

## 5. 预演楔子 + 工作台 UI

沿「算清楚、不碰主区」加能力。工作台是其中对人最有感的一块：**把仓库管理并进去，变成多仓脉搏，而不是再开一个「仪表盘」页叠一套列表。**

### 5.1 信息架构

现状侧栏：`状态 | 合并 | 历史 | 仓库管理 | 操作日志 | 设置`，默认 `/` → `/status`（没选仓时状态页空）。仓库管理里还堆着克隆任务。

目标：

```
侧栏：工作台 | 任务 | 状态 | 合并 | 历史 | 操作日志 | 设置
默认：/ → /dashboard
/repos → /dashboard（兼容旧 hash）
```

| 页 | 职责 |
|----|------|
| **工作台** | 打开 / 克隆入口 / 全仓脉搏。不依赖「已选当前仓」也能用 |
| **任务** | 全部后台任务，按 kind 分组；日志抽屉；失败克隆可改参重试 |
| **状态** | 单仓写操作、更改树、分支图、记录（stash/备份/reflog） |
| **合并** | 单对预演 + 矩阵（不变） |
| **历史 / 日志 / 设置** | 不变 |

侧栏「当前仓库」盒子保留：工作台点一行即 `activate`，状态/合并/历史跟这份当前仓。进行中任务角标挂在 **任务** 菜单，不挂工作台。

### 5.2 工作台布局

工作台一个页面、两块纵向铺满，不再和任务列表抢高度。暗色、行高 `--gc-line`、与现网状态页同一套密度。

```
┌─ 工作台 ──────────────────────────────────────────────┐
│ 打开 [ 本地路径 ___________ ] [打开]   [克隆到本地]    │
├───────────────────────────────────────────────────────┤
│ 全部 12  卡住 1  有更改 4  未同步 2                       │
│ （卡片墙铺满，内部滚动）                                │

│ │ 名 分支│ │ …     │  左条=注意力；底=12 周×7 日热力     │
│ │ ▦▦▦▦ │ │       │                                     │
│ └───────┘ └───────┘                                     │

└───────────────────────────────────────────────────────┘

┌─ 任务 /jobs ──────────────────────────────────────────┐
```

- 一句：打开本地仓库或从远程克隆
- 两个主按钮：打开 / 克隆
- 不引导去状态页

### 5.3 数据：`RepoOverview`

工作台和 `git_repo_overview` 共用。**不要**对每个仓拉完整 `getStatus` 文件列表。

```ts
interface RepoOverview {
  id: number;
  path: string;
  name: string;              // 路径最后一段
  available: boolean;        // 目录还在且是 git 仓
  current: string;           // 分支短名；detached 如实
  tracking: string | null;
  ahead: number;
  behind: number;
  dirtyCount: number;        // staged + unstaged + untracked，冲突另计
  conflictCount: number;
  operation: 'none' | 'merge' | 'rebase';
  tempMergeBranchCount: number; // 本地 merge/* ，与矩阵「已解决·本地」同口径
  activityStart: string;        // 窗口第一天（周一）
  activity: number[];           // 84 个日计数，旧→新
  activityTotal: number;
  lastOpenedAt: string;
}
```

实现：

- core：`GitService.getOverview()`（`status` porcelain + `rev-parse` + 数 `refs/heads/merge/*` + `git log --all --date=short --since` 热力），不读 diff
- 进程壳：`GET /api/repos/overview`；已打开的 N 个仓 **并行**（每仓自己的 GitService，不共享队列）
- 单仓失败（路径没了）→ `available: false`，不拖垮整表
- 缓存：进程内按 `repoPath` 缓存，该 path 的 `repo-changed` 或手动刷新失效。工作台不 1s 轮询
- 前端：进页拉一次；SSE `repo-changed` 只刷新对应行；「刷新」按钮整表重拉

规模：先按「本机已打开 ≤ 50 仓」设计。再大也不做分页，只靠筛选。

### 5.4 工作台交互与现页关系

| 动作 | 行为 |
|------|------|
| 打开路径 | 现 `POST /api/repos`，成功则当前仓=它，**留在工作台**（看到新行），不强制跳状态 |
| 进入 | `activate` + `/status`（与现「进入」相同） |
| 合并 | `activate` + `/merge` |
| 克隆完成 | 现逻辑：open 进列表；工作台该行应很快有 overview |
| 移除 | 现确认文案（不删磁盘） |
| 当前仓 | 行左侧点或高亮；侧栏路径同步 |

状态页、合并页 **不**改成多仓。工作台是唯一多仓面。

### 5.5 楔子上后续可加的能力（工作台之后，按需）

排在工作台与 Job 稳定之后，**不是**工作台的同一期：

| 能力 | 做法 | 不做 |
|------|------|------|
| worktree 一等公民 | 列表/添加/删除走 GitService；落盘已在用，只是暴露 | 不当成第二套工作区随便 merge |
| cherry-pick / revert 预演 | 与 merge-tree 同构：只读结论 + 冲突路径，落盘独立 worktree | 不在本期工作区 `operation` 里做 cherry-pick 收尾（types 已注明） |
| 多仓 fetch | Job kind=`fetch`，工作台可「刷新远程」勾选多行 | 不做成自动定时后台 |

### 5.6 工作台验收

- `/` 进工作台；无仓时能完成打开或克隆，不必先会用状态页
- 卡片能区分干净 / 脏 / 领先落后 / 工作区 merge；点「合并」进对的仓
- Agent `git_repo_overview` 与卡片数字同源
- 侧栏不再有「仓库管理」重复入口

## 10. P0–P2 实现怎么搞

三块**串行**做，每块合完再开下一块。不在同一轮里搬 Capability、不加 Prompt/Resource、不改三栏选边。

已经提前埋好、实现时对齐即可（不要再发明第二套字段）：

- `packages/web/src/api/types.ts`：`JobKind`（`clone | survey | fetch`）、`title` / `repoPath`、`RepoOverview`
- `packages/web/src/api/client.ts`：`listOverview()` → `GET /api/repos/overview`（后端尚未有）
- `useJobsStore.onProgress` 已能吃 `title` / `repoPath`

后端（`JobManager`、`clone_jobs`、`GitService`、MCP `formatResultForMcp`）仍是旧合同。

### 10.1 硬约束（三块共用）

1. **网页只读 GET 行为不变。** `GET .../diff`、`GET .../show`、`GET .../merge/rehearse` 继续回完整正文。摘要只发生在 **MCP 工具结果**（`formatResultForMcp` / tool handler），不要改 `GitService.rehearseMerge` 的默认 `maxFiles=20`，否则合并页三栏会空。
2. **克隆体验不回退。** P1 换表、换类型之后：`POST /api/jobs/clone`、取消、重启中断、SSE 攒 chunk、成功后 `repoManager.open`，现有 `jobs.test.ts` 必须仍绿。
3. **新 git 通道禁止。** overview 加在 `GitService`；Job runner 调已有 `surveyMerges` / `fetch` / `spawnClone`。
4. **不改工具对外名称。** 只加可选参数（`detail`）和少量新工具（`git_job_*`、`git_repo_overview`）。

### 10.2 P0：摘要输出

**目标**：宿主默认拿到小 JSON；要正文时带 `path` 或 `detail=true`。网页无感。

**切法**：在 MCP 包装层收口，不改 Git 算法。

```
executeTool → result（完整，和现在一样，Web POST /tools 也走这里）
    ↓
formatResultForMcp(exec, { tool, args })
    ↓
summarizeForAgent(tool, result, args)   // 仅 MCP 文本
```

Web `POST /api/repos/:id/tools/:tool` **继续返回完整 `result`**（状态页很少用这些只读工具拉大 patch；合并页走 GET）。若以后 Web 也调 `git_diff` 工具，需要正文时自己传 `detail`。

| 工具 | 默认 MCP 输出 | 要正文时 |
|------|----------------|----------|
| `git_diff` / `git_show` | `files[]` + stats + `truncated`；**去掉 `rawPatch`** | `path` 已限定单文件，或 `detail=true`，才带 patch（仍受 `maxPatchBytes`） |
| `git_merge_rehearse` | 与 preview 同形：`outcome` / `clean` / `conflictFiles[].path`，**去掉 `conflictContent` / ours/theirs/base** | 带了 `path`，或 `detail=true`（`maxFiles` 仍生效） |
| `git_merge_preview` | 已经够短，原样 |
| `git_merge_survey` | 已经只有路径，原样；格子数 > 20 的异步放到 P1 |
| `git_file_content` | 超 64KB 只回 `{ path, truncated: true, bytes }` | `detail=true` |
| 写操作 / dry-run | 不改 `WritePreview` | — |

handler 侧为避免白算：MCP 调 `git_merge_rehearse` 且无 `path`、无 `detail` 时，**直接调 `previewMerge`**，不要先 `rehearseMerge` 再扔掉正文。

**改哪些文件**

| 文件 | 做什么 |
|------|--------|
| `mcp-server/src/tools/format.ts`（新建） | `summarizeForAgent` + 现 `formatResultForMcp` 迁过来；成功时先一行 hint，再 JSON（无 pretty 大缩进） |
| `mcp-server/src/tools/handlers.ts` | `formatResultForMcp` 改 re-export，避免循环 |
| `mcp-server/src/tools/schemas.ts` | `GitDiff` / `GitShow` / `GitMergeRehearse` / `GitFileContent` 增加可选 `detail: boolean` |
| `mcp-server/src/tools/index.ts` | rehearse 无 path/detail → `previewMerge`；diff/show 把 `detail` 传进 summarize 所需的 args |
| `mcp-server/src/mcpServer.ts` | instructions 补一句：大结果默认摘要，正文加 `path` 或 `detail` |
| `packages/mcp-server/README.md` | Breaking：默认不再整包 diff3 |
| 测试 | `format.test.ts`：假的超大 rehearse/diff → 输出不含冲突正文 / rawPatch；带 `detail` 则含。`executeTool.test.ts` 里现有 merge rehearse 断言若查的是 `exec.result`（完整对象）**不要改**；另加一条对 `formatResultForMcp` 的 |

**不改**：`gitService.ts` 默认、`webServer.ts` 的 GET merge/diff、`ConflictResolvePanel`、core 的 merge 单测。

**P0 完成标准**：无 `path` 的 `git_merge_rehearse` MCP 文本里没有 `<<<<<<<`；网页打开冲突预演三栏仍有正文。

### 10.3 P1：Job 泛化

**目标**：克隆变成第一种 kind；表和引擎能挂 survey；`POST /api/jobs/clone` 仍可用。

分两步，**同一次落地可以一起交，但测试先绿 clone 再接 survey**。

#### 第一步：换皮（克隆行为不变）

```
core
  types: Job / JobKind / JobProgress
  jobStore.ts     读写 jobs 表；migrate 从 clone_jobs 灌入
  db.ts           CREATE jobs；若存在 clone_jobs 则 INSERT SELECT 后 DROP
  jobs/engine.ts  从 mcp-server JobManager 挪过来并改名 JobEngine
  jobs/kinds/clone.ts  现 runClone

mcp-server
  jobs.ts         薄封装：startClone() → engine.start('clone', { url, destDir })
  webServer.ts    仍调 startClone；SSE 字段加 title/repoPath，clone 继续带 url/destDir
```

`Job` 字段按 §4.1。clone 的 `payload = { url, destDir }`；`title` 用 url 或路径末段；列表 `summary` 为了旧前端仍可带 `url` / `destDir`（从 payload 摊出来）。

迁移 SQL 大意：

```sql
CREATE TABLE IF NOT EXISTS jobs (id, kind, status, title, repo_path, repo_id, payload, logs, result, error, progress, started_at, finished_at);
-- 若 clone_jobs 存在：
INSERT INTO jobs SELECT id, kind, status, url, NULL, repo_id,
  json_object('url', url, 'destDir', dest_dir), logs, NULL, error, NULL, started_at, finished_at
  FROM clone_jobs;
DROP TABLE clone_jobs;
```

`node:sqlite` 无独立 migration 版本表就用「表在不在」判断：有 `jobs` 则不再读 `clone_jobs`。

`JobEngine` 从现 `JobManager` 抄：restore 中断、200ms 节流、pending chunk、MAX 30、取消 AbortController。差别只有 `start(kind, payload)` 查 runner。

**并发**：clone 仍按 `destDir` 互斥。同仓 `survey`/`fetch` 互斥放到第二步。

**测试**：把 `mcp-server/test/jobs.test.ts` 改 import `JobEngine`（或继续测薄封装）；加一条「旧库只有 clone_jobs → 打开后 list 看得到」。

#### 第二步：挂上 survey + MCP 查任务

| 项 | 做法 |
|----|------|
| runner `survey` | payload：`{ intos, froms, fetch, remote, repoPath }`；内部 `git.surveyMerges`；格子循环里若已有 abort 则停；`progress.current/total`；`result` = 现 survey 返回值 |
| 阈值 | `intos.length * froms.length > 20` 或参数 `async=true` → 工具/REST 立即回 `{ jobId, status: 'running' }` |
| 同步仍保留 | 格子少且未要求 async → 现 `surveyMerges` 直接回，**不**造 job（网页矩阵第一期继续同步 GET，避免合并页大改） |
| MCP | `git_job_list` / `git_job_get` / `git_job_cancel`（readonly / readonly / write）；`git_merge_survey` schema 加 `async` |
| REST | `POST /api/jobs` `{ kind, payload }`；`/api/jobs/clone` 内部转 clone，文档标兼容 |
| fetch kind | P1 只留类型与 runner 空位或最小单仓 fetch；工作台「多选刷新远程」放到 P2 之后，P1 不必做 UI |

网页矩阵继续走 `GET .../merge/survey`。Agent 要大矩阵才走 Job。P1 **不改 MergeView**。

**P1 完成标准**：旧克隆路径 E2E/单测绿；库里旧 clone 行升上来；MCP 能 `git_job_get` 到一条 clone；survey 21 格 + `async=true` 返回 jobId，完成后 `result` 有格子。

### 10.4 P2：工作台

**目标**：`/` 进工作台；仓库管理并进去；多仓脉搏与 `git_repo_overview` 同源。

**后端先于 UI**（没有 overview，页面只能继续只显示路径+时间）：

**UI：工作台仍用 `ReposView`；任务另开 `JobsView`，不在工作台叠第二套仓库列表。**

| 文件 | 做什么 |
|------|--------|
